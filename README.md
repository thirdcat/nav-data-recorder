# nav-data-recorder

iOS app for navigation model training data collection.

Records synchronised GPS, IMU, camera video, LiDAR depth and 6-DoF camera pose
from an iPhone, and gets the result off the device either through the Files app
or an automatic background upload.

## What it captures

| Stream | Rate | Source |
| --- | --- | --- |
| GPS position, speed, course | ~1 Hz | CoreLocation, `bestForNavigation` |
| Compass heading | ~1 Hz | CoreLocation |
| Accelerometer, gyro, attitude | 100 Hz | CoreMotion `CMDeviceMotion` |
| Camera video | 30 fps HEVC | ARKit `capturedImage` |
| LiDAR depth | 5 Hz, 256×192 float16 | ARKit `sceneDepth` |
| Camera pose + intrinsics | per frame | ARKit `ARWorldTrackingConfiguration` |

Everything is stamped in one monotonic clock, so video PTS values are
numerically equal to the matching pose timestamps. See
[docs/DATA_FORMAT.md](docs/DATA_FORMAT.md).

ARKit is the only camera client, deliberately: an `AVCaptureSession` and an
`ARSession` cannot share the camera, and taking everything from a single
`ARFrame` means the RGB frame, its depth map, the pose and the intrinsics all
carry one timestamp — frame-perfect synchronisation instead of correlating
independent streams after the fact.

## Building without a Mac

There is no `.xcodeproj` in this repo. It is generated by XcodeGen from
`project.yml` on a cloud macOS runner, signed from an App Store Connect API key,
and delivered to the phone via TestFlight — so the whole loop is push → build →
install, with no Mac and no Xcode anywhere in it.

Setup is in [docs/SETUP.md](docs/SETUP.md). The trade-off is that nothing is
compiled until CI runs it.

## Reading a session

```bash
python3 tools/read_session.py /path/to/20260807-014530-a1b2c3
python3 tools/read_session.py <dir> --align          # one row per video frame
python3 tools/read_session.py <dir> --depth-frame 0  # depth map statistics
```

`tools/read_session.py` is standard-library only; numpy is used for depth arrays
if present. To exercise it without a phone:

```bash
python3 tools/make_test_session.py /tmp/fixture
python3 tools/read_session.py /tmp/fixture/20260807-014530-fixture
```

## Operating constraints

These come from the hardware and iOS, not from the app:

- **The camera does not record in the background.** iOS suspends capture when
  the app is not frontmost. GPS and IMU keep going; video and depth stop. The
  app holds the screen awake while recording, which means it expects a car mount
  and a charger.
- **It gets hot.** ARKit + LiDAR + HEVC is close to a worst-case thermal load.
  By default video and depth pause at `serious` thermal state and resume when it
  drops back, so a long drive degrades instead of dying. Every transition is
  logged to `events.jsonl`.
- **Storage is the real limit on drive length** — roughly 6 GB/hour at defaults.
  Recording stops automatically at 2 GB free.
- **Location must be set to “Always”** in iOS Settings, not just “While Using”,
  or the GPS track ends when the screen locks.

## Layout

```
App/
  Info.plist
  Sources/
    App/        SwiftUI entry point, background-upload app delegate
    Core/       master clock, persisted settings
    Models/     sample structs, session manifest
    Capture/    ARKit / CoreLocation / CoreMotion recorders, video encoder
    Storage/    session directory layout, buffered JSONL and binary writers
    Upload/     background URLSession upload queue
    UI/         record, session list, settings
docs/           setup and data format
tools/          Python session reader and fixture generator
project.yml     XcodeGen spec (the .xcodeproj is generated, never committed)
codemagic.yaml  CI: generate → build → sign → TestFlight
```

## Status

Early. The capture pipeline, storage format and upload queue are written; the
